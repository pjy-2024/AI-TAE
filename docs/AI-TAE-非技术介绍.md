# AI-TAE · 给非技术朋友的项目介绍

> 用途：面向非技术读者的项目通俗介绍。全文不用术语堆砌，打比方为主。
> 真实情况与规划已用 ✅（已完成）/ 🚧（进行中）标注；V2 数字一律【待实测】，不编造。

## 一句话

**它是个「AI 帮软件测试打下手」的引擎：AI 负责把最费人的测试活儿先干一遍，人只做最后把关。**

## 背景：软件上线前为什么要测试

手机 App / 网站上线前都要检查有没有毛病，干这活的人叫**测试工程师**。检查分两种：

- **查功能口子（接口测试）**：后台每个功能口（注册/登录/发一条待办）能不能正常用。≈ 检查餐厅后厨每道菜按菜单做对没有。
- **查界面操作（UI 测试）**：模拟真人去点网页——填表、点按钮、看跳转。≈ 安排「神秘顾客」按普通用户路径把店走一遍。

两种都能写成**自动化脚本**让电脑半夜自己跑，但写脚本、维护脚本非常费人——这正是本项目要解决的。

## 项目解决的两个真痛点

### 痛点一（V1，✅ 已完成并真实验证）
**写接口测试用例太费人。** AI 照着「接口说明书」（OpenAPI，软件自带的接口文档）自动写测试草稿，人审一遍就能用：**从零手写 → AI 初稿 + 人审阅**。
实测：对一个真实开源待办网站 todo_app 的 19 个接口，AI 生成测试并真实执行，通过率 100%（2026-09-03）。

### 痛点二（V2，🚧 正在做）
**网页一改版，旧测试脚本就全废。** 检查单写「点左上角第三个按钮」，网站改版按钮挪走改名后，脚本全扑空、一片红——修脚本是测试团队最烦的隐性成本。
V2 让 AI 看到改版后**自动把检查单改对**，但改之前必须让老师傅（人）点头，防止 AI 把「真出 bug」错当「改版」。

## 运用场景

- 接手新项目：丢接口文档 → 一键得到一批测试草稿（V1）。
- 项目频繁改版：让 AI 先给修复方案，人确认后应用，经验越攒越值钱（V2）。
- clone 即复现、每步有真实记录：可作为作品集展示。

## V2 通俗版（配 docs/images/v2-heal-flow.png 看图）

```
UI 测试失败：按钮/输入框找不到了（定位失败）
  → ① 错误签名：把「哪里失败 + 页面长啥样」压成指纹
  → ② 查自己的笔记本（KV 缓存）：这个指纹 100% 见过？
       ├─ 见过 → 直接抄上次答案（零 AI 调用，最快最便宜）
       └─ 没见过 → ③ 查资料库（RAG）：有很像的案例吗？
            ├─ 有 → 拿相似案例当参考 → 问 AI
            └─ 都没有 → ④ 问专家（LLM）：看新页面给修复建议
  → ⑤ 老师傅（人）看改动确认 → 应用 → 重跑验证
  → ⑥ 经验写回笔记本+资料库（下次同样的坑秒出）
```

为什么搞三层不直接全问 AI：AI 又慢又花钱。**先翻自己笔记本 → 再翻资料库找相似 → 最后才打电话问专家**——最贵的动作放最后。
为什么必须人工确认：QA 最怕 AI 把真 Bug 当改版悄悄修了（测试变绿但线上是坏的）。所以：只对「元素找不到」自愈、修复默认人工确认、记录改动前后 diff。

## 技术栈一句话（给稍懂技术的人）

Python + 对真实开源项目 todo_app 做实验；AI 走 OpenAI 兼容接口（DeepSeek）；V1 用 requests 打接口、V2 用 Playwright 驱动你系统的 Edge 点网页；本地 KV=diskcache、向量库=ChromaDB、记录=SQLite；刻意手写 pipeline 不引 LangChain，每一环都讲得清。
