## 二、30 秒电梯陈述 + 项目脉络速览

### 2.1 电梯陈述（开场用，数字待实测后替换）

我发现 UI 自动化测试最大的隐性成本是「页面一改、脚本就废」的维护。我实现了一个 AI 测试辅助引擎：接口文档进来自动生成用例初稿；元素变化导致失败时，先查本地历史修复库，查不到再让大模型给出修复，并记录真实的自愈成功率与耗时；最后用 golden 标注评测 LLM 判定「真 Bug / Flaky」的准确率。

## 三、讲解主线（按此讲故事，别背题）

1. 背景：UI 自动化脆弱、AI 生成测试两大难题（跑不起来 / 无法证明能发现缺陷）、真 Bug 与 Flaky 难区分。
1. 真实问题：脚本维护成本是 QA 团队的隐性大头；AI 生成用例质量无法量化。
1. 我的决策：不做套壳 ChatBot，把 LLM 嵌入 生成 → 自愈 → 判定 三个真实环节；手写 pipeline 不引 LangChain；先本地校验再落盘；先查缓存再问模型。
1. 取舍：V1 完整 + V2 核心子集 + V3 最小原型；本地嵌入式 KV/向量库而非分布式；被测项目固定 commit 保证可复现。
1. 真实数据：【待实测】→ 可执行率、通过率、自愈成功率、缓存命中率、judge 一致率、成本。
1. 踩坑：依赖漂移（被测项目按 2024 底依赖跑，追最新 starlette 会 500）；沙箱无注册表权限导致环境用纯解压方式重建。
## 四、高频问题与参考答案

### 4.1 HR / 主管面

#### Q1 为什么做测试方向？和考研怎么平衡？

答：软件工程专业，主考研、求职为保底。选测试/测开是因为它离工程质量近、能结合 AI 做实事；时间管理上用时间盒：考研前只做轻量选型与文档，初试后集中 2-3 周冲刺，仓库 commit 历史可以证明节奏。

#### Q2 这个项目和别人调 API 的 demo 有什么区别？

答：三层区别：1) 有工程可靠性设计（Schema 约束+本地校验+限次重试、429 退避、结构化日志）；2) 有成本与延迟意识（先 KV 缓存再 RAG 再 LLM，并真实统计命中率）；3) 有评测闭环（golden 标注算一致率），能证明 AI 判定可信。

#### Q3 你怎么证明项目真实落地？

答：证据链：真实开源被测项目+固定 commit；真实 commit 历史；README 架构图+截图（待 V1）；所有指标来自实际运行日志并注明口径；可 clone 复现（环境路径、依赖、启动命令都写了文档）。

#### Q4 遇到最大的困难是什么？

答：选一个「够真实又不膨胀」的范围，以及环境重建（D 盘只读 → C 盘独立环境）。后者让我真正理解环境可复现的价值：venv、依赖锁版本、被测项目固定 commit，都是为了「别人能复现我的结果」。

### 4.2 技术一面（项目细节）

#### Q5 LLM 生成的用例可执行率多少？怎么提高？

答：【待实测】。提高手段（设计上已定）：LLM 输出必须是结构化 JSON（不是裸 Markdown）；本地 ast 静态校验 + 结构校验；失败时把精确错误回传做限次重试；落盘后统一文件头与 conftest 约定，消除低级错误。（已落地：src/aiae/parser/codec.py + src/aiae/generator/——语义层限次重试会把「结构/代码校验失败原因」追加进对话让模型对照改写。）

#### Q6 429 怎么处理？重试会不会重复计费？

答：只重试可安全重试的错误（429/5xx/连接超时），不重试 400/401 等请求错误；429 优先读 Retry-After，否则指数退避+抖动；每次调用记录 token 用量与重试次数，成本可核算。重复计费风险：请求已计费时盲目重试会二次计费，所以限定重试上限且只对服务端类错误重试。（已落地：src/aiae/llm/client.py，关掉 SDK 自带重试自实现决策表；15 个 mock 测试不联网验证。）

#### Q7 自愈的准确率/误修率？怎么防止把 Bug 当页面变化修掉？

答：【待实测】。设计护栏：只对「元素定位失败」类错误自愈；修复默认人工确认；记录自愈前后 diff；统计误修率口径，而不是只报成功率。

#### Q8 KV 缓存命中率多少？为什么还要 RAG？

答：【待实测】。设计：缓存 key = 错误签名（错误类型+元素特征+页面指纹），命中则零 LLM 调用；KV 只解决「完全见过」的精确命中，RAG 解决「相似但没见过」的模糊检索，两者互补；命中率低也要能讲清原因（数据量、签名粒度）。

#### Q9 为什么用 ChromaDB 不用 ES？数据量多大？

答：数据量小（个人/小组使用，几万条以内），本地 CPU 嵌入式足够，零运维；ES 是多实例/大数据量/分布式检索的正解，属于杀鸡用牛刀。取舍核心是数据规模决定架构。

#### Q10 Judge 怎么证明可信？golden 数据怎么来的？

答：golden = 人工标注样本（计划 50-100 条，SQLite 存储），标注规则先写死（真 Bug / Flaky / 用例问题三类），再算 judge 与人工的一致率；不吹「双模型投票=正确」，一致率不高就如实报告并分析偏差点。

#### Q11 成本怎么控制？生成 100 条用例花多少钱？

答：【待实测】。设计：只在失败时调 LLM；命中缓存不调；重试限次；记录每次调用的 prompt/completion tokens，按单价估算，留日志可追溯。

#### Q12 parser 为什么做归一化（防腐层）？$ref 怎么处理？

答：接口文档差异很大（Swagger 2.0 vs OpenAPI 3.x、参数内联 vs $ref、body 写法不同），如果不收敛，差异会漏进生成器每一层。parser 把外部格式差异隔离在单一模块，生成器只认自己的 Operation 结构——防腐层思想，换被测项目时只改/只测这一个模块。$ref 递归解析成真实结构（生成器要直接读字段，不留指针）；只支持文档内引用，外部文件引用明确报错；递归带栈检测，同一 ref 出现两次即判循环报错。真实文件：src/aiae/parser/openapi.py；真实样例 19 个 Operation / 17 path 解析通过，35 个测试。

#### Q13 换一个 Swagger 2.0 的老项目怎么办？

答：2.0 没有 requestBody，body/formData 是 parameters 里的两项；组件区叫 definitions；响应 schema 直接挂 response 对象；media type 由 consumes/produces 声明。实现上做「最小桥接」：definitions 搬进 components/schemas 并重写 $ref 前缀、body/formData 转 requestBody、响应 schema 包一层 content、参数顶层 type 收进 schema 子对象，再复用同一套 OpenAPI 3.x 归一化——归一化只实现一份，避免双轨逻辑漂移。桥接范围刻意收敛到生成器需要的差异点，host/basePath（服务地址）不归本层管。

### 4.3 技术二面（底层 / 系统）

#### Q14 如果设计成多用户 / 上 CI，架构怎么改？

答：现状是单机嵌入式（SQLite/ChromaDB/diskcache）。上多用户：引入用户/项目隔离，KV 与向量库加命名空间，SQLite 换 Postgres，diskcache 换 Redis，任务队列化（异步生成），结果落库+审计；上 CI：被测项目与生成的用例分离，Docker 沙箱执行，产物与指标上报。

#### Q15 LLM 生成代码的安全风险？怎么隔离？

答：生成代码可能含恶意/错误逻辑。对策：默认只在测试环境执行；Docker 沙箱（断网、只读被测代码、资源限制）；应用前人工确认；静态初筛（危险调用黑名单）作为第一道防线。

#### Q16 自愈流程的完整时序？

答：失败捕获（错误签名）→ 查 KV 缓存 → 命中则直接应用候选修复；未命中 → 查 RAG 相似案例 → 仍未解决 → 组织上下文问 LLM → 输出修复建议 + diff → 人工确认 → 应用 → 重跑 → 结果写回 KV/RAG（形成经验沉淀）。

#### Q17 如果换一个模型，系统会崩吗？

答：不会。两重保障：1) 只依赖 OpenAI 兼容公共子集 chat/completions，模型/地址走配置；2) 输出受 JSON Schema 约束 + 本地校验，模型变了不合格输出会被拦截并重试。换模型后跑一遍评测回归（golden 一致率、可执行率）确认无退化。

#### Q18 被测项目怎么保证可复现？（依赖漂移）

答：真实踩过坑：被测项目按 2024 底依赖写（fastapi 0.115.6 / starlette 0.41），装最新 starlette 1.6 后所有 Jinja 页面 500（TemplateResponse 签名变了）。对策：被测项目按其 lock 时代版本运行 + 固定 commit f3cf7eeb...，不追最新；这也解释了为什么「固定版本 + 锁依赖」是工程必修课。

## 六、额外需要考虑的事项（工程化与面试加分）

### 6.1 工程化

- 可复现：被测项目固定 commit、Python 版本固定（3.12）、依赖清单分层（requirements / requirements-dev / 未来 v2）。
- License 合规：被测项目 todo_app 为 MIT，可注明来源与 commit。
- 可观测性：每次生成/修复/判定写结构化日志（耗时、token、重试、结果），是回答「怎么定位一次自愈失败」的底气。
- 产物纪律：生成用例、缓存、数据库进 data/（gitignore），人工确认后才入库——证据链干净。
- README 证据：架构图（已有）→ 截图（V1 后）→ 演示视频（V3 后）。
### 6.2 面试加分

- 诚实口径：报数前先说分母；没测就说没测并给出测量方案。
- 可讲取舍：为什么不用 LangChain / ES / Redis / 双模型投票——每个都能给一句理由。
- 给面试官「钩子」：主动提到「我踩过依赖漂移的坑」这类具体细节，引导他追问你准备过的部分。
### 6.3 明确不做（防止范围膨胀，也是守时盒）

- 不做多租户/账号体系、UI 录制器、企业级 CI 插件、V3 双模型投票（时间富余再说）。
## 七、雷区与红线（违反=造假嫌疑）
