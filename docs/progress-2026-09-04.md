## 附：Prompt「状态码纪律」实验（2026-09-04 第二轮，真实）

动机：第一轮 fastapi_crud_todo 通过率 66.7%（2 例失败=LLM 自建资源后凭惯例断言 201，被测实际 200）。
尝试：generator `_SYSTEM_PROMPT` 增加硬性要求第 5 条「状态码纪律：断言一律以 responses 声明为准；
自建子请求同；不要凭 REST 惯例假设（如默认 201）」，并加测试保护（143 通过）。

结果（同一被测、同一 DeepSeek、均无人工修正；第二轮生成到 data/generated_tests_fastapi_crud_todo_v2）：

| 轮次 | 生成 | 执行(p/f/e) | 可执行率 | 通过率 |
|---|---|---|---|---|
| ① 无规则 | 6/6 | 4/2/0 | 100% | 66.7% |
| ② 加规则 | 6/6 | 3/3/0 | 100% | 50.0% |

结论（真实、重要）：
1. 光加一句规则无效：LLM 在自建子请求上仍写 201（3 例同病；①的 read_todo 是 404 场景未自建，
   ②改成自建所以多挂 1 例，通过率反而降）；
2. 根因：prompt 只给了「当前接口」的 responses，LLM 看不到 POST /todos/ 的 responses
   → 规则说「以 responses 为准」但模型手里没有那份 responses，只能靠经验猜 201；
   教训：Prompt 工程 = 指令 + 信息，缺一不可；
3. 真正解法方向（未实施，待本人定）：A) prompt 附带被测「全接口成功码速查表」；
   B) 把「资源 id 由框架 resource fixture 提供」与认证形态解耦（无认证项目也可用 fixture，
   去掉 LLM 自建代码这一整类风险：201/307/字段漏传等）。

## 附 2：方案 B 实施（资源能力与认证形态解耦，2026-09-04，真实）

背景：附 1 实验证明「光加规则无效」（LLM 看不到自建子请求对应接口的 responses，只能猜 201）。
决定实施方案 B：把「资源 id 由框架 resource fixture 提供」与认证形态解耦——无认证项目也可声明
resource，conftest 注册无认证资源 fixture（headers={}，不需登录头），generator 对 id 类接口
提示用 created_todo_id fixture、明令 LLM 不要自建。

改动文件：
- src/aiae/targets/fastapi_crud_todo.py：+FastAPICrudTodoResourceAdapter（POST /todos/ 直接取 id），
  resource 从 None 改为声明资源；覆写 resource_id_instruction（无 auth 文案，含「不要自己先调用创建接口」）
- src/aiae/runner/__init__.py：conftest none 分支支持 resource（注册无认证资源 fixture）
- src/aiae/generator/__init__.py：_interface_instruction 重构——none 模式若 resource 且 id 形参则给 fixture 指令
- src/aiae/targets/base.py：契约 docstring 明确资源与认证解耦
- tests：+4（targets 1 / generator 2 / runner 1），全量 147 通过

真实三轮对比（同一被测 fastapi_crud_todo、同一 DeepSeek、均无人工修正、junit 均在 data/runs）：
| 轮次 | 方案 | 生成 | 执行(p/f/e) | 可执行率 | 通过率 |
|---|---|---|---|---|---|
| ① | 无规则（LLM 自建） | 6/6 | 4/2/0 | 100% | 66.7% |
| ② | 加规则（无信息支撑） | 6/6 | 3/3/0 | 100% | 50.0% |
| ③ | 方案 B（框架 fixture） | 6/6 | 6/0/0 | 100% | 100% |

todo_app 回归（password 形态不受影响）：19/19。
结论：与其「让 LLM 少犯错」，不如「让 LLM 没有机会犯那类错」——资源准备从 LLM 代码移到框架 fixture，
201/307/字段漏传等「自建子请求」整类风险消失。这是架构取舍：适配契约多承担一点，生成质量上限更高。
